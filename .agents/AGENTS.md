# エージェント指示書 (Agent Instructions)

本プロジェクトは、**「ソース（始まり）からシンク（終わり）へと流れる構造のカードデッキを使って、中国語の会話を定型文で練習できるゲーム」**です。
今後、AIエージェントを活用してデッキの拡張、機能追加、およびコードベースの保守を行っていきます。

AIエージェントとして本プロジェクトのコードやデータに変更を加える際は、以下のルールと方針を必ず遵守してください。

## 1. プロジェクトの基本目的と構造
- ユーザーが中国語の自然な会話フローを反復練習できるようにする。
- デッキ（カード群）は、特定の会話状態（ノード）と、次の会話への選択肢（エッジ）からなる有向グラフを形成する。

## 2. 厳守事項（Must-Haves）

### A. 「ソース・シンク構造と到達可能性」の維持
デッキの有向グラフは、常に**「すべてのノードがソースから到達可能であり、かつ必ずシンクで終わる構造（Source-Sink Structure）」**でなければなりません。
- **定義**: ソースは入ってくるエッジがない（または会話の起点となる）ノード、シンクは出ていくエッジがない（`next: []`）ノードです。どのノードも孤立してはならず（必ずいずれかのソースから到達可能）、かつ無限ループや行き止まりがあってはなりません（必ずいずれかのシンクへ到達可能）。中間のやり取りでの自然なループ（キャッチボール）は許容されます。
- **指示**: 新しいカード（ノード）や選択肢（エッジ）を追加・変更・削除する場合は、必ず上記の到達可能性条件を満たしているかを論理的に検証し、満たさなくなるような変更は行わないこと。

### B. 会話の自然さの追求
- 追加または修正する中国語のフレーズ（定型文）やその応答は、文脈として不自然でない、実際のネイティブが使用する自然な会話表現を心がけること。
- 前後のカードの繋がり（Q&Aの整合性、話題の遷移など）が論理的かつ自然であることを確認すること。

### C. 拡張性を意識した設計とデータ構造
- 今後AIが自動的にコンテンツを拡張しやすいように、データ（カードの定義やグラフ構造）とロジック（画面描画やゲームの進行制御）は完全に分離しておくこと。
- デッキデータは JSON などの機械可読性が高く、構造が明確なフォーマットで管理し、スキーマの一貫性を保つこと。
- コードベースに変更を加える際は、モジュール化を心がけ、他のコンポーネントへの副作用を最小限に抑えること。

### D. UI/UXデザインの厳密な準拠（Material Design 3）
- ユーザーインターフェースの実装やデザイン変更を行う際は、必ず **[Material Design 3 (M3)](https://m3.material.io/)** の仕様を厳格に守ること。
- **カラーシステム**: M3の Baseline Theme などの Tonal Palettes を使用し、エレベーション（高さ）は影ではなく Surface Tones（`surface-container` などの明るさ）で表現すること。
- **タイポグラフィとアイコン**: Roboto フォントを基準とし、M3のタイプスケールに従うこと。アイコンには Material Symbols を使用すること。
- **コンポーネントの形状と状態**: ボタン（完全な角丸）、チップ（角丸8px）、テキストフィールドなどの形状や、ステートレイヤー（ホバー時の色被せなど）の M3 ガイドラインを忠実に再現すること。

## 3. 追加の推奨ガイドライン

- **変更時のテスト/検証**:
  デッキ構造を変更した際は、提供されている検証スクリプト（`test.sh` および `test/validate_graph.cpp`）を実行し、到達不能ノードや無限ループがないか確認するプロセスを思考に含めること。
- **コメントとドキュメント**:
  新しいロジックを追加した際や、複雑な会話の遷移を追加した際は、その意図が後続のAIエージェントや開発者に伝わるよう、簡潔なコメントを残すこと。
- **エラーハンドリング**:
  想定外のデータが読み込まれた場合（リンク切れなど）にゲームがクラッシュしないよう、適切なフォールバック処理やエラーログ出力の仕組みを維持・強化すること。
